# Linux: вопросы на интервью

Топ вопросов с senior DevOps/SRE интервью в Google, Meta, Cloudflare (2025-2026).
Фокус: рассуждение на уровне ядра, а не знание флагов команд.

## Процессы и планировщик

### В: В чём разница между процессом и потоком на уровне ядра? Как их обрабатывает планировщик Linux?

**Слабый ответ:** «У процесса своя память, а поток разделяет память с другими потоками.»

**Сильный ответ:**
На уровне ядра Linux **нет отдельной концепции потока** — и процессы, и потоки представлены структурой `task_struct`. Разница — в том, какие ресурсы они разделяют, что задаётся флагами при вызове `clone()`:
- `fork()` → новый `task_struct`, новое адресное пространство (copy-on-write), новая таблица файловых дескрипторов
- `pthread_create()` → новый `task_struct`, но разделяет `mm_struct` (память), таблицу fd, обработчики сигналов (через `CLONE_VM | CLONE_FILES | CLONE_SIGHAND`)

CFS (Completely Fair Scheduler) планирует сущности `task_struct` — он не различает процессы и потоки. Каждый получает `vruntime` (виртуальное время выполнения), планировщик всегда выбирает сущность с наименьшим `vruntime`. Это значит, что процесс с 4 потоками получает в 4 раза больше CPU, чем однопоточный процесс с тем же nice — частый источник неожиданного потребления CPU.

**Уточняющий вопрос, который обязательно последует:** что такое переключение контекста и что сохраняется/восстанавливается?
- Сохраняется: регистры CPU, program counter, stack pointer, kernel stack, указатель `mm_struct`
- TLB сбрасывается при переключении процессов (дорого), но НЕ при переключении потоков (то же адресное пространство)
- Поэтому переключение контекста потока ~в 10 раз дешевле, чем процесса

### В: Что такое виртуальная память? Объясни page tables, TLB и что происходит при page fault.

**Сильный ответ:**
Виртуальная память даёт каждому процессу иллюзию владения всей адресуемой памятью. Ядро ведёт **page tables** — многоуровневую структуру (4 уровня на x86-64: PGD → PUD → PMD → PTE), отображающую виртуальные номера страниц в физические номера фреймов.

**TLB (Translation Lookaside Buffer)** — кеш CPU для записей page table. Обращение по виртуальному адресу: проверить TLB → hit: сразу используем физический адрес (быстро) → miss: обходим page tables (~100 циклов, дорого).

**Схема page fault:**
1. CPU не находит трансляцию → генерирует прерывание page fault
2. Запускается `do_page_fault()` ядра
3. Три варианта:
   - **Minor fault**: страница есть в памяти, но не отображена (например, после fork с COW) → просто обновляем page table, без I/O
   - **Major fault**: страница на диске (вытеснена в swap) → читаем из swap/файла, обновляем page table, возобновляем процесс
   - **Недопустимый доступ**: SIGSEGV

**Практическая ценность:** процесс с большим количеством major page fault активно свопируется — смотри `sar -B`, `vmstat`, `/proc/PID/status` (MajFlt). Если видишь это на контейнере — лимиты памяти слишком малы.

### В: Как OOM killer выбирает жертву? Как его настроить или предотвратить срабатывание?

**Сильный ответ:**
Когда ядро не может выделить память, `oom_kill_process()` выбирает жертву по оценке `oom_badness()`:

```
score = (RSS + страницы swap) / total_memory × 1000
score += oom_score_adj  # диапазон: -1000 до +1000
```

- `oom_score_adj = -1000`: никогда не убивать (kernel threads, init)
- `oom_score_adj = +1000`: убить первым

**Настройка:**
```bash
# Защитить критический процесс
echo -500 > /proc/$(pidof postgres)/oom_score_adj

# Сделать процесс первым кандидатом на убийство (например, кеш, который можно перезапустить)
echo 800 > /proc/$(pidof memcached)/oom_score_adj

# Посмотреть текущую оценку
cat /proc/$(pidof myapp)/oom_score
```

**Стратегии предотвращения:**
1. Устанавливай лимиты памяти контейнерам — OOM срабатывает внутри cgroup до системного OOM killer
2. Настрой `vm.overcommit_memory`: `0` = эвристика, `1` = всегда разрешать (опасно), `2` = не выделять сверх `vm.overcommit_ratio`
3. Добавь swap — даёт запас, но следи за латентностью
4. Используй `vm.panic_on_oom=1` на критичных системах, где лучше перезагрузиться, чем доверить выбор OOM killer

**Что смотреть после OOM:**
```bash
dmesg | grep -i "killed process"
journalctl -k | grep oom
```

### В: Объясни copy-on-write (COW) в fork(). Какие практические последствия?

**Сильный ответ:**
При вызове `fork()` Linux не копирует память родителя. Вместо этого:
1. Потомок получает новый `task_struct` и page tables, указывающие на те же физические фреймы
2. Записи page table родителя и потомка помечаются как read-only
3. При первой записи любым из процессов → page fault → ядро выделяет новый фрейм, копирует страницу, обновляет PTE пишущего процесса → оба теперь имеют отдельные копии

**Практические последствия:**
- `fork()` сам по себе — O(1) вне зависимости от размера процесса (копируются только page tables + task_struct)
- COW-страницы копируются только при записи — поэтому read-heavy потомок (например, pre-fork воркер веб-сервера) дёшев
- **Проблема COW в Redis**: `BGSAVE`/`BGREWRITEAOF` использует fork. Если родитель (обрабатывая записи) модифицирует много страниц во время сохранения, COW вызывает массовое копирование → память удваивается. Смотри `rdb_last_cow_size` в `INFO persistence`. Решение: тюнинг интервалов `save`, планирование сохранений в периоды низкой записи.

## Память

### В: Как диагностировать процесс, застрявший в D-состоянии (uninterruptible sleep)?

**Сильный ответ:**
D-состояние (`TASK_UNINTERRUPTIBLE`) означает, что процесс ждёт I/O и не может быть прерван сигналами — даже `SIGKILL`. Частые причины: зависание NFS, медленный дисковый I/O, баг ядра.

**Диагностика:**
```bash
# Найти процессы в D-состоянии
ps aux | awk '$8 == "D"'
# или
cat /proc/*/status | grep -A1 "^Name:" | grep -B1 "^State:.*D"

# Получить kernel stack — где именно завис
cat /proc/<PID>/wchan          # имя функции, в которой ждёт
cat /proc/<PID>/stack          # полный call stack ядра (нужен root)

# Если это I/O
iostat -x 1                    # проверь высокий await на устройстве
ls -l /proc/<PID>/fd           # какие файлы открыты
```

**Решение:**
- Зависание NFS → примонтируй с опциями `soft,timeo`, или исправь NFS-сервер
- Дисковый I/O → проверь `dmesg` на ошибки хранилища, `smartctl -a /dev/sdX`
- Если ничего не помогает: единственный выход — перезагрузка (или kernel panic через `alt+sysrq+f` в крайних случаях)

## Сеть

### В: Опиши путь пакета в сетевом стеке Linux — от прерывания NIC до recv() в user space.

**Сильный ответ:**
```
NIC получает пакет
  → DMA в ring buffer в RAM
  → аппаратное прерывание (hardirq)
  → IRQ handler ядра: минимальная работа, планирует NAPI poll
  → softirq NET_RX_SOFTIRQ: извлекает пакеты из ring buffer
  → netif_receive_skb(): передаёт sk_buff вверх по стеку
  → IP-уровень: решение о маршруте, netfilter hooks (PREROUTING)
  → TCP-уровень: сборка, проверка sequence number, генерация ACK
  → буфер приёма сокета (sk->sk_rcvbuf)
  → процесс вызывает recv() → syscall → ядро копирует данные в user buffer
```

**Ключевые тюнабли и их практическое значение:**
```bash
# Размер ring buffer (дропаем пакеты, если очередь NIC переполнена)
ethtool -g eth0
ethtool -G eth0 rx 4096

# Буфер приёма сокета
sysctl net.core.rmem_max            # максимальный recv buffer сокета
sysctl net.core.netdev_max_backlog  # длина очереди пакетов до дропа

# Бюджет softirq (пакетов за один запуск)
sysctl net.core.netdev_budget       # по умолчанию 300

# Проверить дропы RX
ethtool -S eth0 | grep drop
cat /proc/net/softnet_stat          # колонка 3 = throttled (бюджет исчерпан)
```

## Производительность

### В: Как диагностировать высокую загрузку CPU на Linux? Расскажи про инструментарий.

**Сильный ответ (с правилом mitigation-first):**

Сначала **снизить impact** в production: проверить, можно ли перенаправить трафик, горизонтально масштабироваться или перезапустить проблемный процесс.

Затем диагностируем:

```bash
# 1. Верхний уровень: что потребляет CPU?
top -b -n1 | head -20
# Смотрим: %us (user), %sy (system/ядро), %wa (ожидание I/O),
#          %hi (hardware irq), %si (softirq)

# 2. Разбивка по процессам
pidstat 1 5            # CPU на процесс, 5 замеров

# 3. Высокий %sy → время в ядре, проверяем частоту syscall
strace -c -p <PID>     # счётчики + время syscall (осторожно в prod)
perf top               # живое профилирование kernel+user

# 4. Высокий %wa → ожидание I/O
iostat -x 1            # %util, await по устройству
iotop                  # I/O по процессам

# 5. Найти горячую функцию (perf flamegraph)
perf record -g -p <PID> sleep 30
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg

# 6. Проверить насыщение runqueue
vmstat 1               # колонка 'r' > кол-во CPU = насыщение
sar -q 1               # длина runqueue во времени
```

**Красные флаги:**
- Высокий `%si` + дропы в `cat /proc/net/softnet_stat` → переполнение ring buffer NIC
- Высокий `%sy` на K8s-ноде → часто переполнена таблица `conntrack` или слишком много iptables правил
- Всплеск D-состояния → зависание I/O (см. выше)

## Ядро

### В: Что такое mmap? Когда использовать его вместо read()?

**Сильный ответ:**
`mmap()` отображает файл (или анонимную память) напрямую в виртуальное адресное пространство процесса. Обращение к этой области вызывает page fault, который подгружает данные файла в память по требованию, минуя явный syscall `read()`.

**Когда mmap выигрывает:**
- **Произвольный доступ к большим файлам**: seek + read — O(seeks), mmap позволяет ядру самому управлять prefetch
- **Несколько процессов читают один файл**: file-backed mmap страницы разделяются в page cache — одна копия в RAM независимо от числа процессов (базы данных, shared libraries)
- **Zero-copy паттерны**: `sendfile()` и io_uring используют схожие kernel-space отображения

**Когда read() выигрывает:**
- Последовательное потоковое чтение: read() с большим буфером проще, readahead ядра справляется
- Не хочешь занимать виртуальное адресное пространство
- Файл часто меняется (mmap имеет сложную инвалидацию кеша)

**На практике**: JVM использует mmap в Kafka (commit log). Elasticsearch использует mmap для индексных файлов Lucene. Именно поэтому этим приложениям нужен тюнинг `vm.max_map_count`:
```bash
sysctl -w vm.max_map_count=262144
```

## Шпаргалка: диагностические команды

```bash
# Информация о процессе
ps auxf                          # дерево процессов
/proc/<PID>/status               # память, состояние, потоки
/proc/<PID>/maps                 # отображения памяти
/proc/<PID>/fd                   # открытые файловые дескрипторы
lsof -p <PID>                    # открытые файлы

# Память
free -h                          # обзор
vmstat 1                         # статистика виртуальной памяти
cat /proc/meminfo                # подробно
slabtop                          # slab allocator ядра

# CPU
mpstat -P ALL 1                  # утилизация по CPU
perf stat -p <PID>               # аппаратные счётчики
/proc/loadavg                    # load average

# Сеть
ss -tlnp                         # слушающие сокеты
ss -s                            # статистика сокетов
cat /proc/net/dev                # статистика интерфейсов
netstat -s                       # статистика протоколов (устаревшее, но полезное)
conntrack -L | wc -l             # использование таблицы conntrack
sysctl net.netfilter.nf_conntrack_max

# Диск
iostat -x 1
lsblk
findmnt
df -ih                           # использование inode
```
